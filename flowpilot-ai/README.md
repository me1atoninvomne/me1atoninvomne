# FlowPilot AI

**Weniger manuelle Arbeit. Weniger Fehler. Mehr Zeit fürs Geschäft.**
*Wir automatisieren Ihre Auftrags- und Dokumentenprozesse, ohne Ihre bestehenden Systeme ersetzen zu müssen.*

FlowPilot AI — B2B-SaaS для немецкого Mittelstand (производство, логистика, оптовая торговля, закупки, обработка заказов). Система читает входящие письма и PDF-вложения (заказы, счета, подтверждения заказов, накладные, запросы КП, уведомления о задержках), извлекает данные, сверяет их с мастер-данными ERP, находит расхождения и передаёт сотруднику только те случаи, где действительно нужен человек. Руководитель видит исключения и рассчитанный эффект автоматизации.

Это работающий MVP, а не макет: каждый документ демо-сценария — настоящий PDF, который проходит тот же пайплайн, что и загруженный пользователем файл.

## Быстрый старт

Требования: Node.js ≥ 22.

```bash
npm install
npm run dev            # http://localhost:3000
```

Откройте `http://localhost:3000` → **„Demo starten“**. Регистрация, почтовый ящик и API-ключ не нужны. База данных (SQLite/libSQL, файл `data/flowpilot.db`) и миграции создаются автоматически при первом запросе.

Полезные команды:

| Команда | Что делает |
|---|---|
| `npm run dev` | Dev-сервер (Turbopack) |
| `npm run build && npm start` | Production-сборка и запуск |
| `npm run typecheck` | Проверка TypeScript |
| `npm test` | Unit- и интеграционные тесты (Vitest): домен, ROI, guardrails, весь пайплайн на демо-корпусе |
| `npm run test:e2e` | E2E-тесты (Playwright) — см. [Тесты](#тесты) |
| `npm run db:generate` | Сгенерировать SQL-миграцию после изменения `src/server/db/schema.ts` |

## Демо за 2 минуты

Кнопка „Demo starten“ (после подтверждения «18+ и в рабочих целях») создаёт **изолированное рабочее пространство** для каждого посетителя (cookie `fp_ws`). Можно выбрать отраслевой шаблон: Produktion, Großhandel, Logistik, Einkauf, Auftragsabwicklung. Данные полностью синтетические: вымышленные компании, домены `.example`, несуществующие коды банков, телефонные номера из диапазонов для вымышленного использования.

1. **Posteingang → „Posteingang verarbeiten“.** Около десяти писем проходят пайплайн в реальном времени: чтение текста → классификация → извлечение полей → сверка с мастер-данными → валидация → правила → решение. Каждый шаг выполняется на сервере; анимация лишь слегка замедлена, чтобы за ней можно было следить.
2. **Prüfung → заказ NF-2026-1187.** Клиент заказал по старой цене (412,00 € вместо 438,50 € по рамочному договору). Видны оригинальный PDF с подсветкой найденного места, поля с уровнем уверенности, объяснение («почему это важно»), рекомендация и причина, по которой документ передан человеку.
3. **Исправить цену или принять отклонение с обоснованием → „Freigeben“.** Заказ уходит в Demo-ERP-Sandbox как **черновик** (`DEMO-AE-0001`). Ничего не проводится и не оплачивается.
4. **Счёт с изменённым IBAN.** Критический признак мошенничества. Принять его может только тимлид, а подтвердить после этого — только второй человек (**Vier-Augen-Prinzip**). Переключить демо-пользователя можно в меню справа вверху.
5. **Exception Radar, ROI & Analyse, Aktivitätsprotokoll** — что требует внимания, какой эффект и кто что сделал.

Дополнительно: „Neue E-Mail simulieren“, загрузка собственного PDF (с текстовым слоем), смена отрасли, сброс демо, переключение DE/EN, „Demo-Daten löschen“ (немедленное удаление всех данных пространства).

## Архитектура

```
Next.js 16 (App Router, TypeScript, Tailwind 4)
│
├── src/app/(marketing)      Landing, Preise, ROI-Rechner, Demo, Kontakt   ← публичные страницы
├── src/app/app/**           Приложение (server components → read-модели)
├── src/app/api/**           REST route handlers (zod-валидация, коды ошибок)
│
├── src/domain/              ЧИСТАЯ бизнес-логика, без фреймворка, покрыта тестами
│   ├── validation.ts        Smart Validation
│   ├── routing.ts           guardrails и решение auto | review | approval | ignore
│   ├── rules.ts             движок no-code-правил
│   ├── roi.ts               ROI-калькулятор и измеренный ROI
│   ├── templates.ts         отраслевые шаблоны (workflows, правила, допущения)
│   └── permissions.ts       роли → права
│
├── src/server/
│   ├── documents/           PDF → текст с раскладкой, классификатор, экстрактор, генератор PDF
│   ├── ai/                  абстракция провайдера: demo-rules | anthropic
│   ├── pipeline/            analyze.ts (цепочка без хранения), summary.ts
│   ├── services/            processing, review, config, queries, audit, workspace
│   ├── integrations/        реестр интеграций, интерфейс ErpConnector + Demo-ERP
│   ├── auth/session.ts      сессия демо + RBAC
│   └── db/                  Drizzle-схема (SQLite/libSQL), миграции в /drizzle
│
├── src/i18n/                типизированные словари DE/EN, форматирование (EUR, de-DE, Europe/Berlin)
└── src/components/          UI-примитивы, оболочка приложения, экраны
```

Принципы:

- **AI-провайдер только классифицирует и извлекает.** Валидация, маршрутизация, права и одобрения детерминированы и находятся в `src/domain`. Смена модели не меняет правила безопасности.
- **Интеграции создают только черновики.** Освобождение заказа, проведение счёта или платёж остаются действием человека в целевой системе.
- **Мультиарендность:** каждая бизнес-таблица содержит `workspace_id`, все запросы фильтруются по нему.
- **Секреты только на сервере.** API-ключи читаются из переменных окружения, в клиент не попадают.

## Пайплайн обработки и guardrails

```
E-Mail ─► Text (pdf.js / E-Mail-Text) ─► Klassifizieren ─► Extrahieren ─► Stammdaten-Abgleich
       ─► Validieren ─► No-Code-Regeln ─► Entscheidung ─► { Auto → ERP-Entwurf | Prüfung | Freigabe | Ignorieren }
       ─► Aufgabe / Benachrichtigung ─► Audit-Log ─► ROI-Messung
```

Порядок приоритета решения (`src/domain/routing.ts`):

1. **Системные guardrails, не настраиваются:** критические находки, отсутствующие обязательные поля, неизвестный партнёр, нет текстового слоя, уверенность ниже порога → всегда проверка человеком.
2. Правила, которые требуют проверки.
3. Требования к одобрению: **финансовые документы никогда не одобряются автоматически**, лимиты сумм, правила `require_approval`, процесс без разрешения на автоматическую обработку.
4. Автоматическая обработка — только если workflow это разрешает, сумма в пределах лимита **и** явно сработало включённое правило „weiter“.

Документ, который правил человек, никогда не уходит дальше молча: после исправления нужно явное подтверждение. Каждое решение сопровождается списком причин; они видны на экране проверки и в журнале.

## Модель данных

`workspaces` (tenant, настройки), `users` (роль, отдел), `emails`, `documents` (PDF как blob, текст, извлечение, находки, маршрутизация — JSON), `tasks`, `workflows` (параметры автоматизации, версия), `rules` (no-code), `audit_events` (append-only), `notifications`, `erp_records` (песочница Demo-ERP), `master_data` (снимок ERP: клиенты, поставщики, артикулы, рамочные цены, заказы, полученные счета), `metric_weeks` (недельные агрегаты; `synthetic=true` у демо-истории), `leads` (заявки на консультацию со статусом согласий и хэшем личной ссылки), `consent_records` (доказательства согласий: формулировка, версия, язык, источник), `privacy_requests` (запросы субъектов данных со сроком ответа).

Схема: `src/server/db/schema.ts`, миграции: `drizzle/`.

## ROI: формулы

```
Время сейчас        = документы × ручные минуты / 60
Время после         = (автоматизируемые × минуты контроля + остальные × ручные минуты) / 60
Высвобождённое время = время сейчас − время после
Стоимость времени    = высвобождённые часы × полная стоимость часа
Чистый эффект        = стоимость времени − плата за платформу
Окупаемость          = стоимость внедрения / чистый эффект   (только если эффект > 0)
```

Высвобождённое время **не выдаётся** за денежную экономию. Интерфейс разделяет «Freigesetzte Arbeitszeit», «Potenzielle Einsparung» и «Bestätigte Kostensenkung» (последняя вводится вручную и только при наличии подтверждения). Отрицательный результат показывается честно. В демо время ручной проверки реально измеряется на экране проверки; базовые минуты — явные допущения, их можно менять в настройках.

## Подключение реальных сервисов

### AI-извлечение (Claude)
1. `AI_PROVIDER=anthropic`, `ANTHROPIC_API_KEY=…` (опционально `AI_MODEL`).
2. Демо-пространства всегда используют локальный адаптер; Claude работает только для рабочих пространств с `is_demo = false`.
3. Перед продуктивным использованием: оценка на размеченной выборке реальных документов (precision/recall по полям), договор об обработке данных (AVV), проверка у специалиста по защите данных.

### Microsoft 365 / Outlook
Реализовать `MailConnector` по образцу демо-ящика (`src/server/services/workspace.ts → insertEmail`): регистрация приложения в Entra ID, разрешение `Mail.Read` с ограничением на функциональный ящик (Application Access Policy), Admin Consent, получение писем через Change Notifications или Delta Query, затем `insertEmail()` → `processEmail()`.

### ERP (SAP S/4HANA, SAP Business One, Dynamics 365 Business Central, DATEV)
Реализовать интерфейс `ErpConnector` (`src/server/integrations/demo-erp.ts`). Метод `stage()` должен создавать **только черновик или staging-запись**: Sales Order Draft, Vorerfassung. Мастер-данные (`MasterData`) загружать через тот же коннектор вместо демо-снимка. Нужен технический пользователь с минимальными правами.

### OCR
Подключить сервис перед шагом `extractLayout` (облачный в регионе EU или локальный) и возвращать `TextLayout` с координатами строк.

### SSO
Заменить cookie демо-сессии на OIDC (Entra ID), роли выводить из групп. Проверки прав (`s.require(...)`) остаются без изменений.

### Хранилище и база данных
Для нескольких инстансов использовать libSQL/Turso (`DATABASE_URL`) или перенести Drizzle-схему на PostgreSQL. PDF-файлы в продакшене лучше хранить в S3-совместимом хранилище в регионе EU, а не в БД.

## Безопасность и защита данных

Реализовано: Content-Security-Policy (`default-src 'self'`, браузер не обращается ни к одному стороннему домену), HSTS по `HSTS=1`, ограничение частоты запросов к публичным endpoint'ам (в памяти, только production), роли и права на сервере, принцип четырёх глаз, append-only журнал аудита, никакой автоматической записи непроверенных данных в критичные системы (только черновики после правил и guardrails), никаких платежей, API-ключи только на сервере, изолированные демо-пространства с автоудалением, правила хранения данных, httpOnly-cookie, security headers, локальные шрифты (без Google Fonts), никаких трекеров, валидация входных данных (zod), PDF отдаётся только владельцу рабочего пространства, бинарная проверка загружаемых файлов (`%PDF-`), лимит размера.

**Соответствие DSGVO/GoBD здесь не заявляется.** Перед продуктивным запуском нужно: хостинг в EU с AVV, TOM-документация, концепция удаления с учётом сроков хранения по HGB/AO, реквизиты оператора и юридическая проверка шаблонов (см. следующий раздел), пентест, SSO, логирование доступа, бэкапы, общее хранилище для rate limiting при нескольких инстансах.

### Что должен сделать оператор перед запуском

1. Заполнить реквизиты (`COMPANY_*` и другие) — `/api/health` покажет `legal.companyDetailsComplete: true`.
2. Отдать тексты `/datenschutz`, `/agb`, `/erstattung`, `/cookies`, `/impressum` юристу и заполнить оставшиеся `[[…]]` (сроки договора, SLA, логи хостинга, договор AVV).
3. Заключить AVV с хостингом и, если включается Claude, — с Anthropic (передача данных в США).
4. Перед первой e-mail-рассылкой — подключить почтовый сервис с Double-Opt-in и заголовками `List-Unsubscribe`/`List-Unsubscribe-Post` на `/api/unsubscribe?t=…`.
5. Провести ручной аудит доступности (автоматические проверки axe не заменяют его) и обновить `/barrierefreiheit`.

Обработка запросов субъектов данных:

```bash
npm run privacy -- list                 # открытые запросы, просроченные — первыми
npm run privacy -- export <email>       # все данные по адресу в JSON (Art. 15/20)
npm run privacy -- erase <email>        # удалить контактные запросы и их согласия (Art. 17)
npm run privacy -- complete <id> [note] # отметить запрос как выполненный
npm run licenses                        # заново сгенерировать список лицензий зависимостей
```

## Тесты

```bash
npm test                                      # 68 unit/integration tests
E2E_BASE_URL=http://localhost:3000 npm run test:e2e   # против запущенного сервера
npm run test:e2e                              # сам запускает `npm start` на :3100 (после build)
```

E2E-наборы (desktop и mobile): `demo-flow` — основной сценарий; `compliance` — баннер cookie, согласия, проверка возраста, удаление данных, отписка, юридические страницы; `a11y` — axe-core (WCAG 2.1 A/AA) на всех публичных страницах, всех страницах приложения, диалоге и баннере; `keyboard` — сценарий только с клавиатуры; `third-party` — ни одного запроса на чужие домены, нет нарушений CSP, заголовки безопасности.

`demo-flow` проверяет основной сценарий через UI: письмо → проверка → принятие отклонения → подтверждение → черновик в ERP → журнал; принцип четырёх глаз со сменой пользователя; smoke-тест всех страниц без ошибок JS и без горизонтальной прокрутки на desktop и mobile; переключение языка.

Если Playwright не может скачать браузер, укажите свой Chromium: `PW_CHROMIUM_PATH=/path/to/chromium`.

Вспомогательные скрипты для визуальной проверки (против запущенного сервера):
- `node scripts/shot.mjs <prefix> /app/inbox /app/review` — скриншоты (`WIDTH=390` для мобильной ширины, `NEWDEMO=1 PROCESS=1` для нового демо с обработкой);
- `node scripts/pdfcheck.mjs out.png` — проверка превью PDF с подсветкой найденного места.

## Деплой

**Docker (self-hosting, например на сервере в Германии):**
```bash
docker build -t flowpilot-ai .
docker run -p 3000:3000 -v flowpilot-data:/app/data flowpilot-ai
```

**Node:** `npm ci && npm run build && npm start` (за reverse proxy с HTTPS).

**Serverless (например Vercel):** SQLite-файл там не сохраняется между запусками, поэтому нужен `DATABASE_URL` на libSQL/Turso.

## Известные ограничения и следующие шаги

- Демо-адаптер настроен на типичные немецкие макеты документов. Для произвольных макетов нужен провайдер на основе LLM, оценка которого ещё не проводилась.
- Нет OCR: сканы честно уходят на ручную обработку.
- Почта, ERP и DATEV пока только в виде интерфейсов и описаний; реальные коннекторы не реализованы.
- Аутентификация — демо-сессия; SSO запланирован.
- Уведомления только in-app.
- Многостраничные PDF: текст извлекается со всех страниц, а превью с подсветкой показывает первую страницу.
- Юридические тексты — шаблоны без проверки юристом; реквизиты оператора не заданы; ручного аудита доступности не было (только автоматические проверки axe и клавиатурный тест).
- Маркетинговые e-mail-рассылки не реализованы (нет Double-Opt-in-письма); согласие и отписка уже хранятся.

Следующий шаг к первому клиенту: пилот на одном процессе (например, Auftragseingang) с подключением функционального ящика M365 и выгрузкой мастер-данных из ERP в формате CSV.
